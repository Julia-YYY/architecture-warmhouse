# Задание 1. Анализ и планирование

### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

-  Включение/выключение отопления в своих домах.

**N.B.** 
Есть расхождение кода и ТЗ: ТЗ описывает управление отоплением как реализованную функцию, тогда как в `apps/smart_home/handlers/sensors.go` эндпоинтов управления нет; реализованы только учёт датчиков и чтение показаний.

**Мониторинг температуры:**

- Просмотр текущей температуры через веб-интерфейс.
- Хранится только последнее показание: `UpdateSensorValue` выполняет `UPDATE` поверх той же строки. Истории наблюдений во времени нет.

**Учёт датчиков:**

- Cоздание, чтение, обновление, удаление, обновление значения выполняются с единственной сущностью `sensors`
- Подключение датчика выполняется не пользователем, а выездом специалиста.

**Управление электричеством (To Be)** 
- Включение/выключение света удаленно

**Управление домом (To Be)**
- Наблюдение за домом
- Закрытин\открытие ворот

**Будущее неуточнённое поведение**

- Подключение устройств заранее неизвестных типов и протоколов без изменения кода служб. Реализуется моделью возможностей, в которой тип устройства является записью в реестре, а не значением перечисления в коде.

**Мониторинг (To Be)**

- Просмотр телеметрии пользователем: ряды наблюдений во времени, а не одно последнее значение.

### 2. Анализ архитектуры монолитного приложения

- **Язык программирования**: Go
- **База данных**: PostgreSQL
- **Архитектура**: Монолитная, все компоненты системы (обработка запросов, бизнес-логика, работа с данными) находятся в рамках одного приложения.
- **Взаимодействие**: Синхронное, запросы обрабатываются последовательно.
- **Масштабируемость**: Ограничена.
- **Развертывание**: Требует остановки всего приложения.
- **Домены**: Визуализируйте контекст системы. Создайте диаграмму контекста (Context diagram) в модели C4 с помощью PlantUML. Диаграмма должна наглядно показывать, как монолитное приложение взаимодействует с внешним миром (пользователи, датчики).

### 3. Определение доменов и границы контекстов

**Домен проекта:** удалённое управление умными устройствами жилого дома по модели SaaS с самообслуживанием.

При определении поддоменов в качестве основного источника правды взят исходный код монолита.

| Поддомен As-Is | Реализация | Состояние |
|---|---|---|
| Учёт датчиков | `handlers/sensors.go:32-43` — CRUD над единственной сущностью | Реализован |

#### 3.2 Поддомены целевой экосистемы (To-Be)

Поддомены целевого проекта классифицированы по трём категориям, для определения стратегии реализации.

| Тип | Определение | Комментарий |
|---|---|---|
| **Core** (ключевой) | Стратегически важные: то, за что клиент выбирает нас, а не конкурента | Разрабатываем сами, сильнейшими специалистами |
| **Supporting** (поддерживающий) | Необходим для работы бизнеса, но конкурентного преимущества не даёт | Разрабатываем сами, максимально просто |
| **Generic** (общий) | Задача, решённая индустрией | Берём готовое решение или внешнего провайдера |

Критерий отнесения к Core: **выберет ли клиент «Тёплый дом» вместо конкурента из-за этого?** Способность может быть критичной для работы системы и при этом не быть ключевой: без телеметрии система неработоспособна, но никто не выбирает поставщика умного дома за качество хранилища данных.

| № | Поддомен | Тип | Основание в ТЗ |
|---|---|---|---|
| 1 | **Подключение устройств** (самообслуживание) | **Core** | «Пользователь самостоятельно выбирает необходимые ему модули… **сам их подключает**» — в противовес As-Is: «Каждая установка сопровождается выездом специалиста» |
| 2 | **Сценарии автоматизации** | **Core** | «настраивает сценарии работы»; «покупатели могут программировать систему для управления различными модулями в соответствии со своими потребностями» |
| 3 | **Интеграция устройств** (протокольные адаптеры, модель возможностей) | **Core** | «поддерживает подключение к экосистеме устройств партнеров по стандартным протоколам»; «Продуман вариант подключения ещё неизвестных датчиков» |
| 4 | Управление устройствами (команды и состояние) | Supporting | «управлять отоплением, включать и выключать свет, запирать и отпирать автоматические ворота» |
| 5 | Телеметрия | Supporting | «просматривает телеметрию» |
| 6 | Дома и объекты | Supporting | «пользователь может иметь доступ к нескольким домам» |
| 7 | Видеонаблюдение | Supporting | «удалённо наблюдать за домом» |
| 8 | Каталог и продажа комплектов | Supporting | «должны быть максимально готовы к использованию и **продаваться в отдельных комплектах** для удобной покупки» |
| 9 | Идентификация и управление доступом | **Generic** | Следует из модели SaaS с самообслуживанием и множественным доступом к домам |
| 10 | Биллинг и подписки | **Generic** | Следует из модели SaaS и продажи комплектов |
| 11 | Уведомления | **Generic** | Отражено на диаграмме контекста как внешний почтовый сервис |

#### 3.3 Проекция поддоменов на ограниченные контексты

| Ограниченный контекст | Включённые поддомены | Обоснование границы |
|---|---|---|
| **Подключение устройств** | 1, 3 | Общий единый язык: возможности, протоколы, учётные данные, привязка к дому. Ядро конкурентного преимущества |
| **Сценарии автоматизации** | 2 | Собственный язык (условие, действие, триггер, расписание). Изменяется по причинам, не связанным с устройствами |
| **Управление устройствами** | 4 | Команды и текущее состояние. Необходима немедленная согласованность |
| **Телеметрия** | 5 | Большие объёмы, запись преобладает над чтением, допускается согласованность в конечном счёте. Профиль нагрузки несовместим с управлением. |
| **Видеонаблюдение** | 7 | Потоковые данные, объёмы хранения и требования к полосе на порядки отличаются от телеметрии; нужно также предусмотреть режим приватности |
| **Дома и объекты** | 6 | Модель владения и доступа, изменяется редко, читается всеми |
| **Каталог и продажи** | 8 | Язык товара: цена, состав комплекта, наличие. Не пересекается с эксплуатационной моделью устройства |
| **Внешние поставщики** | 9, 10, 11 | Реализуются внешними провайдерами |

**Ключевое проектное решение**

Поддомены «управление отоплением», «управление освещением» и «управление воротами», перечисленные в ТЗ отдельно, отображаются на **один** ограниченный контекст «Управление устройствами».

Обоснование: все три подчиняются одной модели (команда и состояние), различен только набор возможностей. Общего у них больше, чем различий; создание отдельного контекста на каждый тип устройства породило бы три почти идентичные модели и сделало бы невозможным выполнение требования о неизвестных датчиках.

Видеонаблюдение выделено в самостоятельный контекст, в силу различия в природе данных: потоковые данные вместо дискретных команд и показаний.

### **4. Проблемы монолитного решения**

**1. Единственная таблица и отсутствие ключевых сущностей.** `init.sql` содержит одну таблицу `sensors`. Таблиц пользователей, домов, типов устройств и истории телеметрии нет. Следствия:

- Модель владения отсутствует. Разграничение доступа не реализовано на уровне данных — любой запрос к `/api/v1/sensors` возвращает все датчики системы. Для SaaS с несколькими арендаторами это блокирующее ограничение.
- Дом как сущность отсутствует. Его роль отведена текстовому полю `location VARCHAR(100)` (`init.sql:12`). Требование «один пользователь может иметь доступ к нескольким домам» на текущей модели невыполнимо.

**2. Историю телеметрии система не хранит.** `UpdateSensorValue` (`db/db.go:232-249`) выполняет `UPDATE`, перезаписывая значение на месте. Хранится только последнее показание. Требование «просматривает телеметрию» подразумевает ряды наблюдений во времени — то есть телеметрия как поддомен в As-Is фактически отсутствует, а не просто ограничена.

**3. Hard-code/magic word: тип устройства зашит в код.** `models/sensor.go:10-12`:

```go
const (
    Temperature SensorType = "temperature"
)
```

Перечисление содержит одно значение. Добавление нового типа устройства сегодня требует изменения кода монолита и его полной остановки при развёртывании. Это подтверждение на уровне кода тезиса ТЗ о неготовности системы к «подключению ещё неизвестных датчиков».

**4. Синхронный опрос с линейным ростом времени ответа.** `handlers/sensors.go:54-67` вызывает внешний API для каждого датчика в цикле при обработке одного запроса; таймаут каждого вызова — 10 секунд (`services/temperature_service.go:33`). Время ответа растёт линейно с числом датчиков, недоступность одного датчика деградирует общий отклик.

**5. Подключение требует выезда специалиста** — операция не масштабируется автоматически.

**6. Ключевая проблема - совмещение\смешение смыслов.**

В cтруктуре `models.Sensor` (`models/sensor.go:15-25`) находятся три различные по смыслу группы полей:

| Группа полей | Поля | Смысловая принадлежность |
|---|---|---|
| Описание модели | `Name`, `Type`, `Unit` | Каталог / тип устройства |
| Экземпляр | `ID`, `Location`, `CreatedAt` | Учёт установленного оборудования |
| Наблюдение | `Value`, `Status`, `LastUpdated` | Телеметрия |

На данный момент в системе есть God Object («божественная» сущность), внутри которого (если не разбить монолит) будет "зашит" разный функционал : три модели с разными жизненными циклами, разной частотой изменения и разными объёмами данных описаны одним типом и хранятся в одной строке таблицы. Показание датчика меняется постоянно, описание типа — практически никогда, но обновление значения физически затрагивает ту же строку.

# Задание 4. Создание и документирование API

### 1. Тип API

**Выбран REST API, описанный в OpenAPI 3.2.**

**Обоснование**
Исходя из операций, показанных на [диаграмме компонентов](diagrams/component/WarmHouse_Component.puml). Все пять описанных операций находятся на рёбрах, помеченных `sync, JSON/HTTPS`: вызовы от API Gateway и службы сценариев к «Управлению устройствами», от «Управления устройствами» к «Шлюзу устройств», чтения открытых служб «Дома и объекты» и «Подключение устройств». Асинхронными на диаграмме являются только рёбра шины Kafka и брокера MQTT: но это публикация и подписка на события домена, и участниками там выступают не клиенты API, а сами службы.


### 2. Документация API

**Документ:** [`diagrams/task_4_api_spec/warmhouse_api_doc.yaml`](diagrams/task_4_api_spec/warmhouse_api_doc.yaml).

Описано пять операций двух микросервисов целевой архитектуры:

| Служба | Операция | Метод и путь | Характер |
|---|---|---|---|
| Управление устройствами | Отправить команду устройству | `POST /device_management/sendCommandToDevice` | async request-reply: `202` + `callbacks` |
| Управление устройствами | Текущее состояние устройства | `GET /device_management/getDeviceStatus` | синхронная |
| Управление устройствами | Возможности устройства или типа | `GET /device_management/getCapabilities` | синхронная |
| Шлюз устройств | Типы устройств по протоколу | `GET /device_gateway/typesByProtocol` | синхронная |
| Шлюз устройств | Зарегистрировать новый протокол | `POST /device_gateway/protocols` | синхронная |

# Задание 5. Работа с docker и docker-compose

Приложение temperature-api реализовано исходя из того, что текущий монолит не "выбрасывается в корзину", а замещается постепенно.
